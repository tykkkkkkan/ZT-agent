# 数据库 P0 升级说明（P0 Database Upgrade Guide）

> 适用版本：Django 6.1 + MySQL 8.0 项目 `agent_db`
> 升级前请**完整备份数据库**（`mysqldump -u root -p agent_db > backup_$(date +%Y%m%d_%H%M%S).sql`）

---

## 1. 升级步骤（生产环境）

### 1.1 备份
```bash
mysqldump -u root -p agent_db > backup_$(date +%Y%m%d).sql
```

### 1.2 在 Navicat 顺序执行以下 SQL（或运行 migration 脚本）

依次执行 3 个 migration 文件中定义的 SQL（按 0004 → 0005 → 0006 顺序）：

```bash
# 1) 生成 0004 的纯 SQL（含 products/inventory/orders/conversations/contact_messages/custom_requests 的 ALTER）
cd D:\TYKKKKKK\Trae\中渔天下\ZT-agent
.venv\Scripts\python.exe manage.py sqlmigrate agent 0004 > migration_0004.sql

# 2) 0005 包含两阶段：先填数据（RunPython）再 ALTER 加 UNIQUE
.venv\Scripts\python.exe manage.py sqlmigrate agent 0005 > migration_0005.sql

# 3) 0006
.venv\Scripts\python.exe manage.py sqlmigrate agent 0006 > migration_0006.sql
```

然后在 Navicat 中按顺序执行 `migration_0004.sql` → `migration_0005.sql` → `migration_0006.sql`。

### 1.3 为存量 products 填 SKU（关键！0005 已包含）
0005 的 RunPython 会自动：
- 遍历 `sku` 为空的 Products
- 按 id 升序填充 `SKU-0001`、`SKU-0002` ...
- 然后把 `sku` 改为 NOT NULL 并加 UNIQUE 索引

**前提**：0004 已把 `sku` 列加好（nullable）。如果跳过 0004 直接 0005 会失败。

### 1.4 记录 migration 状态
让 Django 知道这些 migration 已执行（不需要再 apply）：
```bash
.venv\Scripts\python.exe manage.py migrate --fake agent 0004
.venv\Scripts\python.exe manage.py migrate --fake agent 0005
.venv\Scripts\python.exe manage.py migrate --fake agent 0006
```

### 1.5 验证
```bash
.venv\Scripts\python.exe manage.py check
# 应输出：System check identified no issues (0 silenced).
```

## 2. 升级内容速览

| 改动 | 表 | 说明 |
|---|---|---|
| + sku | products | 人类可读唯一商品编码（`SKU-XXXX`） |
| + is_active | products | 软删除标志（下架不丢历史订单） |

## 3. 回滚

每个 migration 都有 `reverse_sql`，可用：
```bash
.venv\Scripts\python.exe manage.py migrate agent 0003
```
恢复到 0003 之前的状态。

## 4. 注意事项

1. **`makemigrations` 后续会提示 6 个 model 字段与 migration "不一致"**（orders 的 Meta.indexes、contact/custom 的 db_index）：
   - 这是因为 0004 用 RunSQL 直接 ALTER，而 Django 倾向用 operations。
   - **实际 DB 不会重复加索引**（MySQL 会报 Duplicate key，但 0004 还没在生产跑过）。
   - 如果想消除警告：在 Navicat 跑完 0004 之后再写一个 0007 migration 用 Django operations 表达（幂等即可）。
   - 暂时忽略不影响运行。

2. **`managed=False` 的表**（products/inventory/orders/conversations）：
   - Django 不会自动建表
   - 但**字段/索引/约束变更仍能通过 migration 追踪**
   - 切勿改为 `managed=True`（会导致 Django 试图 CREATE 已有表而报错）

3. **存量数据兼容性**：
   - `Orders.status` 从 `NULL` 改为 `NOT NULL DEFAULT '未发货'`：存量 NULL 行会被默认值填充（MySQL 8.0 默认 sql_mode 不严格）
   - `Inventory.stock` 改为 `UNSIGNED`：现有负数会触发严格模式错误 → 升级前先 `UPDATE inventory SET stock=0 WHERE stock<0;`
   - `Products.sku` 从 NULL 填到 NOT NULL：0005 的 RunPython 已保证无 NULL 残留

## 5. 升级后行为

| 操作 | 升级前 | 升级后 |
|---|---|---|
| 创建订单 | 库存不扣减 | 自动预占库存，库存不足返回 400 |
| 标记发货 | 仅 admin 改 status，库存不动 | 事务内：扣减 stock、释放 reserved，写 ship_company/tracking_no/shipped_at |
| 取消订单 | 无状态 | 释放 reserved，状态→已取消，写原因 |
| 退货 | 无状态 | 回滚 stock，状态→已退货 |
| 软删除产品 | 硬删 → 历史订单外键断裂 | is_active=False，产品/历史订单保留 |
| 商品查询 | 只回 id/name | 回 sku / available_stock / is_active |
| AI 客服查产品 | 仅名称价格 | 含 SKU 和可用库存 |

## 7. P1/P2 完善项（第二批次）

### 7.1 留言/定制管理（P1）
- 新增列表接口：`GET /api/agent/contact-msgs/`、`GET /api/agent/custom-reqs/`
  - 参数：`is_read=0|1`（筛选）、`limit`（默认 50，最大 200）、`offset`
  - 返回：`{success, total, has_more, messages|requests: [...]}` 分页元信息
- 删除接口：`DELETE /api/agent/contact-msg/<id>/`、`DELETE /api/agent/custom-req/<id>/`
- 标记已读：`PATCH` 同端点，Body `{"is_read": true}`
- 全部要求 staff 登录（管理员）

### 7.2 RAG 知识库数据化（P2）
- 新增表 `knowledge_chunks`（`agent.models.KnowledgeChunk`，managed=True 自动建表）
  - 字段：`title` / `category`（季节钓法·鱼种钓法·钓法技巧·企业政策·其他）/ `keywords`（逗号分隔）/ `content` / `is_active`
- **首次启动自动 seed**：`knowledge_data.seed_knowledge_to_db()` 把静态 `KNOWLEDGE_BASE`（22 条）幂等写入 DB
- RAG 索引构建：`get_knowledge_rag()` **优先从 DB 加载活跃条目**，DB 不可用回退静态语料
- 后台维护：Admin 侧栏新增「智能问答 → 知识库条目」，可在线增删改
- **注意**：RAG 索引是内存缓存（`_rag_cache`），修改知识库后需**重启 Django 进程**才会重建索引
- 升级后 `products` 表已生成 SKU（SKU-0001 起，按 id 升序）

### 7.3 管理类 API 鉴权（P2）
- 新增 `@staff_required` 装饰器（`agent/views.py`），校验 `request.user.is_staff`
- 应用范围：产品 CRUD / 库存 / 订单状态变更 / 留言定制管理
- 未登录或非 staff → `401 {"success": false, "message": "需要管理员权限，请先登录后台。"}`
- 公开端点（chat/contact/custom/history/产品列表/订单查询）不受影响
- 前端标注：管理功能页调用前需确保浏览器已登录 `/admin/`（session cookie 同源自动携带）

### 7.4 事务回滚修复（真实 bug）
- `create_order_api` 库存不足分支原在 `transaction.atomic` 块内 `return`，
  导致**订单已创建但库存未扣**的脏数据（Django 只在异常传播出块时回滚）。
- 已修复：`except InsufficientStockError` 分支加 `transaction.set_rollback(True)`。
- 实测：下单 999999 件 → 400 `insufficient_stock`，订单数不变（8→8）。
