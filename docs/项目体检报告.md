# ZT-agent 项目体检报告

> 体检日期：2026-10-26  
> 体检方式：只读静态审计、目录/代码量统计、测试配置检查、命令可执行性检查。  
> 结论性质：作品集/毕业设计工程体检，不等同于完整渗透测试、压测或生产验收。

## 0. 结论先行

ZT-agent 已经超过“能展示聊天机器人”的阶段：它有商品、库存、订单、支付凭据、钱包、售后、评价、转人工、后台管理和 RAG 评测等完整业务面，Agent 也具备 Function Calling、ReAct、SSE、工具轨迹和引用来源。这些是求职作品的明显加分项。

但当前不能把它包装成“生产级系统”。最硬的短板有三组：

1. **会话归属边界不完整**：历史、反馈、转人工按客户端传入的 `session_id` 查询，未看到当前用户与会话的绑定校验，存在跨用户读取/写入风险。
2. **认证模型混用且大量 `csrf_exempt`**：同一批接口同时接受 JWT 和 Django Session，浏览器会话接口又关闭 CSRF，管理端风险尤其高。
3. **可复现性未收口**：本机 `.venv` 启动器指向不存在的 Python，`check`、`pytest`、`ruff` 均无法实际执行；测试主要是纯函数和 Mock，真实数据库业务链路仍依赖手工脚本。

**最值得优先改的前三件事**：补齐会话归属与 CSRF 边界；关闭或保护 `test-ai` 并清理默认凭据/密钥兜底；修复测试环境并把订单、支付、Agent 工具链纳入可重复的数据库集成测试。

## 3. 架构评估

### 3.1 总体数据流

```text
浏览器
  -> Django URL / 自定义认证
  -> agent.views.chat
  -> agent.agent.agent_stream
  -> _react_loop
       -> agent.llm.chat_stream（DeepSeek，SSE/流式）
       -> agent.tools.call_tool
            -> 商品/库存/订单/钱包/转人工业务模块
            -> agent.knowledge_data.get_knowledge_rag
                 -> TF-IDF/BM25
                 -> 或 Embedding + Chroma
                 -> 或两路并行 + RRF
  -> SSE 返回文本、商品卡、订单卡、来源和转人工卡
  -> Conversations + AgentRun 落库
```

关键代码路径：

- `agent/views.py:163-240` 接收聊天请求、校验消息并把 Agent 事件包装为 SSE。
- `agent/agent.py:252-305` 负责外层生命周期和轨迹落库；`310-502` 是最多 3 轮的 ReAct 循环。
- `agent/tools.py:849-859` 注册 9 个工具，`1018` 起统一分发。
- `agent/knowledge_data.py:241-259` 负责懒加载、构建、缓存和失败降级。
- `agent/services.py:81-151` 用行锁处理库存；订单状态机从 `331` 起集中处理状态变化。

### 3.2 分层清晰度

**做得好的地方**

- Agent 编排、工具执行、业务事务、RAG 算法已经有文件级分工，不是所有逻辑都堆在一个视图里。
- 订单状态和库存变更有 `transaction.atomic()` 与 `select_for_update()`，库存预占、发货、取消、退货形成闭环。
- 支付凭据使用随机 Token、过期时间、唯一索引、行锁核销，重复确认有防护。
- RAG 有 `tfidf`、`embedding`、`hybrid` 三档，并在语义后端不可用时降级到 TF-IDF。

**结构性问题**

- `agent` 同时承担 HTTP、Agent、领域业务、数据模型、后台和集成脚本，应用边界过宽。
- `agent.tools` 直接引用 `Products`、`Orders`、`Inventory` 等 ORM 模型，并在内部调用 `pricing`、`reviews`、`purchase_guard`；工具层不是稳定的领域端口。
- `me_views.py` 直接导入 `views.py` 的 `_serialize_order`，`views_cashier.py` 直接导入 `views.py` 的 `_resolve_request_user` 和 `_server_error`。这不是当前已确认的循环依赖，但说明共享能力没有单独抽层。
- 通过局部导入规避导入时序问题，降低了启动时循环导入概率，却也使依赖关系不够显式。静态阅读未发现已发生的模块级循环导入，仍建议用导入图和启动测试持续守住。

### 3.3 双路 RAG 与 ReAct 是否讲得清

| 环节 | 实现 | 判断 |
|---|---|---|
| 文档源 | 优先 `knowledge_chunks`，DB 不可用时回退静态知识 | 代码路径清楚 |
| 字面路 | `RAGEngine` 内部 TF-IDF 召回，BM25 重排 | 可解释、零第三方依赖 |
| 语义路 | `OpenaiEmbedder` + `ChromaStore` | 需要外部 API、持久化目录和网络 |
| Hybrid | 两路取候选，按 chunk id 做 RRF 融合；语义失败回退字面路 | 降级逻辑完整 |
| Agent 使用 | `search_knowledge` 读取 RAG 结果，将标题和答案片段喂回 LLM | 入口单一 |
| ReAct | LLM 产生 tool call，工具结果以 `role=tool` 回喂，最多 3 轮后生成答案 | 流程可追踪 |

文档和代码总体能讲清“输入 -> 召回 -> 工具 -> 生成”的主路径，但需要向面试官主动解释两个现实约束：Embedding/Chroma 不是每次请求都必然可用；RAG 缓存是进程内缓存，多 worker 下会重复初始化。

## 4. 风险清单

等级说明：P0=上线前必须处理；P1=高收益优先处理；P2=中期治理；“待确认”表示静态检查无法证明运行时行为。

### 4.1 安全风险

| 等级 | 风险 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P0 | 会话 IDOR：历史接口未校验会话归属 | `agent/views.py:258-276` 仅按 `session_id` 查 `Conversations`；模型没有会话用户外键 | 已登录用户若拿到其他 `session_id`，可能读取对话内容；`feedback` 同样可对任意会话写反馈 | 给会话建立用户归属，所有 history/feedback/handoff 查询都绑定当前用户；历史匿名会话另建一次性访问凭据 |

### 4.2 性能与稳定性风险

| 等级 | 风险 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P1 | 同步阻塞的 LLM 网络调用 | `agent/llm.py:45-60、102、190-217`，超时最高 60 秒并带重试；聊天视图是同步 Django 请求 | 并发上升时 worker 被长时间占用；LLM 抖动会放大请求堆积 | 独立异步/任务队列或 ASGI 方案；设置总预算、熔断和客户端断开取消 |

| P2 | 魔法数字虽有集中趋势但仍散落 | 如 ReAct 轮数、卡片上限集中在 `agent/agent.py:29-32`，但分页、超时、展示截断在多文件重复 | 业务规则调整要搜索多处，容易出现口径漂移 | 统一业务常量/配置对象，测试关键边界 |

- RAG 纯算法覆盖相对最好，且不依赖数据库和网络，适合 CI。

- `scripts/verify_*.py` 有 40 余个业务验收脚本，覆盖地址、支付、钱包、评价、库存同步、转人工、追踪等；它们不是 pytest 自动测试，CI 也没有统一执行。

### 5.3 零测试或测试不足的模块

- `agent/services.py`：订单状态机、库存行锁、钱包流水的真实数据库行为未进入 pytest。

- `agent/tools.py`：9 个工具的大量权限分支、旧订单手机号归属和异常降级未被主测试套件覆盖。
- `agent/admin.py`、`middleware.py`、`coordination.py`、`knowledge_data.py` 的生产路径测试不足。

### 5.4 全量测试耗时

本次尝试执行：

```text
D:\...\ .venv\Scripts\python.exe manage.py check
D:\...\ .venv\Scripts\python.exe -m pytest tests
D:\...\ .venv\Scripts\python.exe -m pytest --collect-only -q tests
D:\...\ .venv\Scripts\python.exe -m ruff check agent config tests
```

结果均未进入 Django/pytest 运行阶段：`.venv\Scripts\python.exe` 是指向已不存在的 Python 3.12 安装路径的虚拟环境启动器，命令分别返回启动失败（测试命令未产生有效测试耗时）。因此：

- **本次不能给出可信的全量测试耗时或通过率**，不能把约 0.05 秒的启动失败耗时当成测试时间。
- 当前测试可执行性本身是 P0/P1 级工程问题。
- 修复解释器后，建议先跑 `pytest tests/ -q --cov=agent --cov-report=term-missing`，再单独执行数据库验收脚本；将真实耗时、失败数和覆盖率固化到 CI 工件。

## 7. 求职视角

### 7.1 加分项

- **业务闭环完整**：商品查询、库存预占、订单状态、支付凭据、钱包、评价、退货和转人工不是孤立 Demo。
- **Agent 不是简单聊天包装**：有 9 个工具、JSON Schema、ReAct 循环、工具结果回喂、最大轮数和轨迹记录。
- **RAG 有工程取舍**：TF-IDF/BM25 提供零依赖兜底，Embedding + Chroma 提供语义路，Hybrid 用 RRF 融合，并有失败降级。
- **并发意识较好**：库存和余额相关路径使用事务、行锁、幂等/状态机思路，支付 Token 有过期和唯一约束。
- **可观测性意识明确**：Request ID、慢请求统计、AgentRun、工具耗时、LLM token 统计、来源引用和后台搜索测试台，面试时很容易展开。
- **有交付意识**：Docker、启动脚本、验收脚本、CI、部署文档和 RAG 评测结果，比只展示源码更接近真实项目。

### 7.2 面试官一定会追问的软肋

1. **为什么 history 只信任客户端 `session_id`？** 当前代码无法证明它属于当前用户，这是最需要先修的安全问题。
2. **为什么大量接口 `csrf_exempt`，又允许 Session 认证？** 需要明确区分 JWT 无状态接口和浏览器 Session 接口。
3. **为什么测试不是全量自动化？** `scripts/verify_*.py` 很多，但核心 CI 只跑少量 pytest；当前本机虚拟环境还无法启动。
4. **`managed=False` 的表如何保证新环境一致？** 需要说明 `agent_db.sql`、Django migrations 和结构验收的边界。
5. **LLM 调用失败、超时、重复重试怎么控制成本？** 需要解释同步 worker、重试、超时、断开连接和降级策略。
6. **RAG 评测指标是什么？** 目前有结果文件和算法测试，但仍应补充固定数据集、Recall@K/MRR/人工评审口径和线上反馈闭环。
7. **Agent 工具如何防止越权？** 不能只回答“Prompt 会提醒模型”，必须展示服务端按用户/角色/订单归属校验。
8. **为什么 `tools.py` 和 `views.py` 这么大？** 面试官会把它作为模块化、可测试性和团队协作能力的追问入口。
9. **前端为什么没有标准构建链和类型系统？** CDN 多页面适合演示，但需要说明在正式项目中会如何拆组件、构建和发布。

## 8. 待确认项

以下事项静态体检无法下确定结论，不能当作“已通过”：

- 真实 MySQL 线上表是否具备模型声明的所有索引、唯一约束和外键。
- 反向代理、HTTPS、CORS、`ALLOWED_HOSTS`、Redis 和 `/metrics` 的生产部署策略。
- `session_id` 是否在前端或网关层已有不可伪造绑定；后端代码当前没有看到足够证据，因此按风险处理。
- Embedding API、Chroma 持久化目录在多进程/多副本部署下的并发一致性。
- 完整 pytest 通过率、耗时和覆盖率；当前被损坏的 `.venv` 阻断。

## 一句话结论

**这是一个业务闭环和 Agent 工程亮点都比较强的毕业/求职作品，但安全边界、测试可复现性和模块拆分还没有收口；先修认证归属、生产入口和测试环境，再谈生产级。**
